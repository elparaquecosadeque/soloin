## Summary

Soloin is a new Angular 22 library (`@gblp/soloin`) that fills a gap none of its sibling packages (`@gblp/chord-finder`, `@gblp/circle-of-fifths`, `@gblp/bass-notes`) address: given a chord progression or a key, it computes the scales that fit and shows exactly which notes to target on a 6-string guitar fretboard, with each chord's tones highlighted in a distinct color. Unlike its siblings, which each hardcode their own ad-hoc note model, Soloin has a real interval/pitch-class theory engine, and unlike its siblings (which only export their Angular component), Soloin exports the engine headlessly too — it's designed as the seed of a future shared `@gblp/music-theory` package.

This is a from-scratch build, scaffolded with `ng new` / `ng generate library`, structured to match `circle-of-fifths`' conventions (the most mature precedent in the family: real vitest tests, 3-workflow CI, `:host` CSS-variable fallback pattern).

### Key Decisions

| Decision | Rationale | Alternatives Considered |
|---|---|---|
| Formula-based theory engine (pitch classes 0–11, scales/chords as interval-step arrays) | Only approach that generalizes to many scale types and stays reusable for a future shared package | Hardcoded per-key tables (circle-of-fifths' style) — rejected, doesn't generalize |
| Own chord parser, independent of chord-finder/chords-db | Needed pitch-class output for interval math; chord-finder's parser/types aren't exported anyway | Depend on `@gblp/chord-finder` — rejected, needs its public-api widened first, wrong data shape |
| Native key detection (scores input against generated diatonic chords) | circle-of-fifths' own key-scoring logic isn't exported; re-deriving it from the new engine avoids a cross-repo dependency | Modify circle-of-fifths to export its scoring logic — rejected, point-to-point coupling works against the eventual shared-package goal |
| Export both component and engine from `public-api.ts` | Deliberate deviation from all 3 siblings (component-only); seeds a future `@gblp/music-theory` extraction | Component-only (match sibling minimalism) — rejected, repeats the "logic trapped inside one package" gap that blocked reusing circle-of-fifths' key detection |
| All progression chords' tones shown simultaneously, color-coded | User's explicit choice over a bass-notes-style prev/next stepper | Step-through playback (bass-notes precedent) — considered, not chosen |
| No component-level theme input | Matches all 3 siblings exactly — theming is pure CSS custom property inheritance | Explicit `theme` signal input — rejected, unnecessary given CSS vars already cover it |

## Technical Context

### Architecture

```
soloin/
├── src/app/                       ← demo shell, imports @gblp/soloin from dist/
├── projects/soloin-lib/
│   └── src/
│       ├── public-api.ts          ← exports SoloinComponent + full engine
│       └── lib/
│           ├── engine/            ← pure functions, no Angular deps
│           ├── components/soloin-fretboard/  ← presentational SVG component
│           ├── export/rasterize.ts            ← PNG/PDF pipeline, dynamically imported
│           └── soloin.ts          ← SoloinComponent, wires engine → fretboard
```

**Engine**: pitch classes are plain numbers 0–11. Scales and chords are both "formula applied to a root" — a scale is an array of semitone steps between degrees, a chord is an array of semitone offsets from the root. The 7 major modes are generated by rotating one 7-element array, not by transcribing 7 separate arrays. `detectKey` scores a parsed chord list against all 24 keys' generated diatonic triads (extended qualities like `m7`/`dom7` reduce to their triad family for matching).

**Theming**: every color in `SoloinFretboard` and `SoloinComponent` is a `var(--_chords-*)` private token, redeclared on each component's own `:host` with a fallback chain back to the public `--chords-*` tokens the-chords defines (`var(--chords-x, <literal-fallback>)`) — circle-of-fifths' pattern, not bass-notes' (which requires the host to define every var). **Both components independently redeclare the shared chord-color/scale-note tokens** because CSS custom properties only inherit down the DOM tree, and `<soloin-fretboard>` and the legend in `soloin.html` are siblings, not ancestor/descendant — see Gotchas.

**Export**: the live SVG uses `var(--_chords-*)`, which an isolated `<img src="blob:...">`-loaded SVG document can't resolve (no inherited custom properties). `rasterize.ts` clones the live SVG, reads each token's resolved value via `getComputedStyle`, and inlines a `<style>` block with the literal values before serializing — then the same Blob → Image → `<canvas>` → `toDataURL` pipeline bass-notes uses applies unchanged.

### Dependencies

Angular 22, TypeScript ~6.0.2, vitest, ng-packagr — no new dependencies beyond what `ng new`/`ng generate library` scaffold by default. No ESLint (matches all 3 siblings — Prettier + `.editorconfig` only).

## Things to Know

### Gotchas & Pitfalls

- **CSS custom properties don't cross sibling boundaries.** The chord-color tokens (`--_chords-chord-color-1..6`) were originally only declared on `SoloinFretboard`'s own `:host`. The legend in `SoloinComponent`'s template is a *sibling* of `<soloin-fretboard>` in the DOM, not a descendant, so it never inherited those tokens and rendered with invisible (unstyled) swatches. Fixed by redeclaring the same token set on `SoloinComponent`'s own `:host` in `soloin.scss`. **If you add a new color token consumed by both the fretboard and the outer component's own template, it must be declared in both `:host` blocks.**
- **`@for` track expressions must be collision-free even for "obviously fine" derived keys.** `soloin-fretboard.html`'s fret-marker loop tracked by `m.cx`, but the two 12th-fret dots (above/below center) share the same `cx` by design — Angular logged `NG0955` for the duplicate key. Fixed by tracking `$index` instead, since `positionMarkers` is a static array.
- **Rebuilding `soloin-lib` while `ng serve soloin` is running can race.** ng-packagr wipes and rewrites `dist/soloin-lib` on each build; if the dev server's incremental rebuild reads mid-write, it errors with a stale/broken bundle. Restart `ng serve` after rebuilding the lib rather than relying on live-reload to catch it.
- **The pitch-class speller is not diatonic-aware.** `noteName()` always renders a pitch class through one fixed sharp/flat table per call, never choosing per-scale-degree spelling (e.g. a scale that theoretically wants `Fb` will show `E` instead). This matches bass-notes' existing simplification and is an accepted ceiling, not a bug — see the `ponytail:` comment in `pitch-class.ts`.
- **The 6-color chord palette cycles via `hue-rotate()` past 6 distinct roots** (`soloin-fretboard.ts`) — fine for realistic guitar progressions, documented as a ceiling in a `ponytail:` comment.

### Assumptions Made

- Standard 6-string guitar tuning only (E-A-D-G-B-E) — no alt tunings or capo support.
- EN/ES only; note names stay fixed English letters in both languages (no solfège), matching sibling convention.
- `detectKey` picks the first-scoring key on ties (loop order: root 0–11, major before minor) — same tie-breaking behavior as circle-of-fifths' own (unexported) key detection.
