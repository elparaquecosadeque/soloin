## Summary

Soloin is an Angular 22 library (`@gblp/soloin`) that fills a gap none of its sibling packages (`@gblp/chord-finder`, `@gblp/circle-of-fifths`, `@gblp/bass-notes`) address: given a chord progression or a key, it computes the scales that fit and shows exactly which notes to target on a 6-string guitar fretboard. Unlike its siblings, which each hardcode their own ad-hoc note model, Soloin has a real interval/pitch-class theory engine, and unlike its siblings (which only export their Angular component), Soloin exports the engine headlessly too — it's designed as the seed of a future shared `@gblp/music-theory` package.

Since the initial build, a series of real-usage sessions (typing actual progressions, comparing against a reference guitar-scale tool, cross-checking the music theory by hand) drove a second wave of substantial features: per-chord Mosaic/Carousel views, a Notes/Degrees label toggle, root markers, a highlighted tonic triad in Key mode, a full CAGED fretboard-box system, a diatonic/non-diatonic check per chord, and typo-tolerant chord parsing with safe "did you mean" suggestions. The repo is now a git repo, pushed to GitHub, with the demo already live on GitHub Pages — only the npm publish is still pending (see Next Steps).

### Second wave (post-initial-build usage sessions)

- [x] **Mosaic/Carousel views**: showing every progression chord's tones overlaid on one board was chaotic once chords shared several tones (rings stacking up); each chord now gets its own compact fretboard (Mosaic, stacked) or you step through them one at a time (Carousel) — a global toggle, not per-tile
- [x] **Scale backdrop hidden by default** (`showScaleNotes`, opt-in checkbox): a chord's own tones are what "belongs" to it; the shared key-wide scale is now an explicit opt-in layer instead of blended in by default
- [x] **Notes/Degrees toggle**: every label can show either note names or scale-degree/interval labels (R, 2, b3, #4...), each hardcoded per scale/chord quality against real theory (`SCALE_DEGREE_LABELS`, `CHORD_DEGREE_LABELS`), not inferred generically
- [x] **Root marker**: the root/tonic of the active scale and of every chord layer gets a ring, in every view, so the eye always has a fixed anchor point
- [x] **Tonic triad in Key mode**: the I (major key) or i (minor key) triad is now highlighted within the full scale, giving Key mode a harmonic anchor instead of 7 undifferentiated dots
- [x] **CAGED fretboard boxes** (`components/soloin-fretboard/caged.ts`): narrows the neck to one of the 5 classic movable hand positions. The anchor-fret math for each shape was derived from real open-chord fingerings (not memorized fret tables) and verified two ways: against a real reference tool's screenshot (F major, E-shape box starts at fret 1 — matched exactly) and against a from-scratch invariant test (the 5 boxes always sort into C-A-G-E-D order, for all 12 possible roots)
- [x] **Diatonic check** (`isDiatonic`): flags, per chord, whether it belongs to the detected/selected key — visible as a badge on every mosaic tile, the carousel label, the legend, and the copy-as-text output
- [x] **Chord-parsing fixes**: bare `"4"` now parses as sus4 (tab-style shorthand, e.g. `"D4"`); unrecognized tokens are surfaced instead of silently dropped, with a Levenshtein-distance "did you mean" suggestion that refuses to guess when the closest candidates would mean musically different things (verified by a test that caught this exact false-positive risk during development)

## Key Decisions

| Decision | Rationale | Alternatives Considered |
|---|---|---|
| Formula-based theory engine (pitch classes 0–11, scales/chords as interval-step arrays) | Only approach that generalizes to many scale types and stays reusable for a future shared package | Hardcoded per-key tables (circle-of-fifths' style) — rejected, doesn't generalize |
| Own chord parser, independent of chord-finder/chords-db | Needed pitch-class output for interval math; chord-finder's parser/types aren't exported anyway | Depend on `@gblp/chord-finder` — rejected, needs its public-api widened first, wrong data shape |
| Native key detection, no changes to circle-of-fifths | circle-of-fifths' own key-scoring logic isn't exported; re-deriving it avoids cross-repo coupling | Modify circle-of-fifths to export its scoring logic — rejected, works against the eventual shared-package goal |
| Export both component and engine from `public-api.ts` | Deliberate deviation from all 3 siblings; seeds a future `@gblp/music-theory` extraction | Component-only (match sibling minimalism) — rejected |
| Mosaic/Carousel instead of one shared overlaid board | Overlapping chord-tone rings on one board became unreadable once chords shared several tones | Kept the original single-board overlay as the only view — rejected after real use surfaced the clutter |
| Scale backdrop opt-in, not on by default | A chord's own tones are "what belongs to it"; blending in the whole key's scale by default blurred that distinction | Always show the scale backdrop — rejected, caused real confusion in testing ("why is this note here?") |
| Degree labels hardcoded per scale/chord (not inferred from semitone distance) | A generic semitone→label table can't pick #4 vs b5 correctly (context-dependent, e.g. Lydian vs Locrian); hardcoding per named scale/quality, like the interval formulas already are, is correct and no more code | Infer degree labels generically from interval distance — rejected, produces wrong labels for Lydian's #4 |
| CAGED box math derived from open-chord positions, not a memorized fret table | Verifiable from first principles (open-chord root positions are unambiguous) rather than trusting recalled "standard" offsets that are easy to get subtly wrong | Hardcode a fret-offset table from memory — rejected as too risky for pedagogical content |
| "Did you mean" suggestions refuse to guess on quality-ambiguous ties | A textual edit-distance tie between candidates that mean *different* chord qualities (e.g. sus2 vs sus4) is a coin flip, not a confident correction; ties that resolve to the *same* quality (e.g. "sus" vs "sus4") aren't real ambiguity and are still suggested | Always suggest the first/any tied candidate — rejected, would produce confident-looking wrong guesses (caught by a test during development, e.g. "D6" almost suggested "Dm") |
| All progression chords' tones shown simultaneously (within a tile/board), color-coded | User's explicit choice over a bass-notes-style prev/next stepper | Step-through playback — considered, not chosen |
| No component-level theme input | Matches all 3 siblings — theming is pure CSS custom property inheritance | Explicit `theme` signal input — rejected, unnecessary |

## Technical Context

### Architecture

```
soloin/
├── src/app/                       ← demo shell, imports @gblp/soloin from dist/
├── projects/soloin-lib/
│   └── src/
│       ├── public-api.ts          ← exports SoloinComponent + full engine (NOT the CAGED module — that's fretboard-internal, not instrument-agnostic theory)
│       └── lib/
│           ├── engine/            ← pure functions, no Angular deps
│           ├── components/soloin-fretboard/  ← presentational SVG component + CAGED box geometry
│           ├── export/rasterize.ts            ← PNG/PDF pipeline, dynamically imported
│           └── soloin.ts          ← SoloinComponent, wires engine → fretboard
```

**Engine**: pitch classes are plain numbers 0–11. Scales and chords are both "formula applied to a root". `detectKey` scores a parsed chord list against all 24 keys' generated diatonic triads. `isDiatonic` reuses that same triad-family matching to answer the question per-chord instead of per-progression. `suggestChordName` only fires when the root parses but the quality suffix doesn't, and only returns a suggestion when exactly one *quality* (not text string) wins within 2 edits.

**Fretboard labels**: `SoloinFretboard` no longer computes note names itself — it renders whatever `toneLabels`/`scaleLabels` strings the caller supplies (`SoloinComponent` switches these between note names and degree labels based on the `labelMode` signal). This keeps the fretboard a dumb renderer and the notes-vs-degrees decision in one place.

**CAGED boxes**: a box is just a fret-range filter applied to the *same* already-correct dot computation — no separate note-selection logic for "boxed" mode, only a `f < box.start || f > box.end` skip in the render loop. The 5 boxes' anchor frets come from where the root note falls on each shape's defining string, offset by that shape's own open-position root fret (C and G shapes root 3 frets into their own fingering; E/A/D root at the nut) — see `caged.ts` for the derivation and its verification tests.

**Theming**: every color is a `var(--_chords-*)` private token, redeclared on each component's own `:host` with a fallback chain to the public `--chords-*` tokens. Both `SoloinComponent` and `SoloinFretboard` independently redeclare the shared chord-color/scale-note/danger tokens, because CSS custom properties don't cross sibling DOM boundaries (see Gotchas).

**Export**: the live SVG's colors AND fonts are custom properties / inline attributes; an isolated `<img src="blob:...">`-loaded SVG can't resolve either from the host page, so `rasterize.ts` clones the SVG, resolves each color token via `getComputedStyle`, inlines them as a `<style>` block, and relies on every text element already carrying its font/size/weight/fill as literal SVG attributes (not CSS classes) in the live template.

### Dependencies

Angular 22, TypeScript ~6.0.2, vitest, ng-packagr — no new dependencies added since the initial build. No ESLint (matches all 3 siblings — Prettier + `.editorconfig` only).

## Things to Know

### Gotchas & Pitfalls

- **CSS custom properties don't cross sibling boundaries.** A color token declared only on `SoloinFretboard`'s `:host` won't reach the legend in `SoloinComponent`'s own template (siblings in the DOM, not ancestor/descendant). Any token consumed by both must be declared in both `:host` blocks.
- **`@for` track expressions must be collision-free even for "obviously fine" derived keys.** Two fret-12 marker dots shared the same `cx` by design — track `$index` for static arrays instead of a derived value that isn't guaranteed unique.
- **Rebuilding `soloin-lib` while `ng serve soloin` is running can race** (ng-packagr wipes `dist/soloin-lib` mid-rebuild). Restart `ng serve` after rebuilding the lib.
- **Fretboard text needs inline SVG attributes, not CSS classes, for anything that must survive export.** The exported SVG is cloned and serialized outside this component's stylesheet, so `font-family`/`font-size`/`fill` set only via a CSS class silently vanish in the exported image — set them as literal attributes in the template.
- **Fuzzy "did you mean" suggestions must be checked by resolved meaning, not surface text.** Two textually-different candidates can tie on edit distance while meaning either the same thing (not real ambiguity — pick one) or different things (real ambiguity — refuse to guess). Checking only the string distance produces convincing-looking wrong answers.
- **The pitch-class speller is not diatonic-aware.** `noteName()` always renders a pitch class through one fixed sharp/flat table, never per-scale-degree spelling. Accepted simplification (matches bass-notes' precedent), documented with a `ponytail:` comment and upgrade path.
- **The 6-color chord palette cycles via `hue-rotate()` past 6 distinct roots** — fine for realistic progressions, documented as a ceiling.

### Assumptions Made

- Standard 6-string guitar tuning only (E-A-D-G-B-E) — no alt tunings or capo support (see TODO.md).
- EN/ES only; note names stay fixed English letters in both languages (no solfège) — deliberately rejected when raised, to match sibling convention.
- `detectKey`/`isDiatonic` reduce extended qualities to a triad family (maj7/dom7/sus2/sus4 → major family, etc.) for matching purposes — a chord can be "diatonic" by this check while still being a color-tone extension of a plain triad.
- CAGED boxes apply uniformly across the whole progression/key (one hand position for everything), not per-chord — matches how the system is actually used in practice.
